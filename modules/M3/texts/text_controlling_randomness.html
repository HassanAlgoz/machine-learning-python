Controlling Randomness

Machine learning algorithms rely heavily on randomness. It is used:

  1. to shuffle your data before training
  2. and to set initial starting points for models to learn from

If you do not manage this parameter correctly:

  1. your code might give you different results every time you run it
  2. you might accidentally run unfair tests when comparing two different models

The Two Ways to Set random_state

The behavior of your code changes drastically depending on exactly what you assign to random_state. You generally have two choices:

Option 1: Passing an Integer (e.g., random_state=42)

When you use a specific number, the internal random number generator resets to the exact same starting line every single time it is called. Result: You get the exact same outcome every time you run that specific step.

Option 2: Passing a RandomState Instance (e.g., random_state=rng)

When you create a specific “random state object” at the top of your code, it acts like a deck of cards. Every time a part of your code asks for randomness, it draws a card from the top of the deck. The next time it asks, it draws a different card. Result: The outcome changes slightly every time you run a step, exploring different random possibilities.

Rule 1: Models (Estimators) should use Instances

A model (like a Random Forest) uses randomness to build itself. When evaluating how good your model is, you want to be certain it is genuinely a good model, and not just performing well because it got “lucky” with one specific random setup.

The Best Practice: Pass a RandomState instance to your models.

When you test the model multiple times, the instance forces the model to use a slightly different random internal setup each time. This proves your model’s performance is robust and reliable, regardless of how its internal random numbers happen to land.

Rule 2: Data Splitters should use Integers

Before training a model, you use a splitter tool (like train_test_split and K-Fold Cross-Validation) to divide your data into “training” sets and “testing” sets.

The Best Practice: Pass an integer to your data splitters.

If you are comparing Model A and Model B to see which is better, the test must be perfectly fair. They must be evaluated on the exact same cut of data. If you pass an instance to the splitter, the deck gets shuffled between testing Model A and testing Model B. You will not know if Model B won because it is a better model, or because it just got an easier batch of test data. An integer locks the shuffle in place.

The Ultimate Setup for Reproducibility

If you want to ensure that a coworker running your script gets the exact same final score you did, you need to control the entire environment from the very top of your script.

  1. Create a single RandomState instance at the very beginning of your code.
  2. Pass that exact same variable down into the random_state parameter of your models.
  3. Use a fixed integer for the random_state of your data splitters.

This guarantees that the total sequence of random events plays out exactly the same way from start to finish, every single time the script is executed.
